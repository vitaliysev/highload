# Deployment Document: Маркетплейс объявлений

## 1. Deployment

### 1.1. Описание развёртывания

#### Назначение

Маркетплейс объявлений — платформа для создания, поиска и просмотра объявлений о продаже товаров. Пользователи создают объявления с описанием и ценой, ищут товары по ключевым словам и фильтрам, оплачивают продвижение объявлений в результатах поиска.

#### Нагрузка

**Профиль трафика:** Read-heavy (95% read, 5% write)

**Нагрузочные тесты:**


| Тест      | Конфигурация                  | RPS (итого) | Thresholds              |
| --------- | ----------------------------- | ----------- | ----------------------- |
| smoke.js  | 5 VUs, 30s                    | ~15         | p95 < 500ms, error < 1% |
| load.js   | 100 VUs browse + 30 VUs write | ~50-60      | p95 < 500ms, error < 5% |
| stress.js | 300 VUs browse + 60 VUs write | ~200-250    | p95 < 2s, error < 20%   |


**Распределение операций:**

- 50% — просмотр карточки объявления
- 35% — поиск по ключевым словам
- 15% — личный кабинет пользователя

#### Сервисы


| Сервис              | Ответственность                                       | Тип       | Zone    |
| ------------------- | ----------------------------------------------------- | --------- | ------- |
| **nginx**           | API Gateway, маршрутизация запросов                   | stateless | private |
| **listing-service** | CRUD объявлений, управление статусами                 | stateless | private |
| **search-service**  | Полнотекстовый поиск, кэширование результатов         | stateless | private |
| **worker**          | Асинхронная обработка модерации из очереди            | stateless | private |
| **postgres**        | Транзакционная БД (объявления, пользователи, платежи) | stateful  | private |
| **redis**           | Кэш карточек и поисковых запросов                     | stateful  | private |
| **rabbitmq**        | Очередь задач модерации                               | stateful  | private |

### 1.2. Стратегия деплоя

#### Listing Service, Search Service, Worker — Rolling Update

**Стратегия:** Rolling Update (обновление реплик по одной)

**Обоснование:** Stateless сервисы без локального состояния. Можно безопасно обновлять инстансы поочередно при масштабировании на несколько реплик.

**Zero-downtime контракт:**


| Аспект            | Реализация                                                             |
| ----------------- | ---------------------------------------------------------------------- |
| Readiness probe   | `GET /health` → 200 OK (проверка доступности PostgreSQL/Redis)         |
| Liveness probe    | `GET /health` → 200 OK                                                 |
| Graceful shutdown | SIGTERM → прекратить прием запросов → завершить активные (30s) → выход |


#### PostgreSQL — Blue-Green для мажорных обновлений

**Стратегия:** Blue-Green deployment (запуск новой версии параллельно, переключение трафика)

**Обоснование:** Stateful компонент с критичными данными платежей. Мажорное обновление (16 → 17) требует pg_upgrade или logical replication. Возможность быстрого отката критична.

**Процесс:**

1. Поднять PostgreSQL 17 (green) параллельно с PostgreSQL 16 (blue)
2. Настроить logical replication (16 → 17)
3. Переключить приложение на green (обновить connection string)
4. Мониторинг 24 часа.

**Zero-downtime контракт:**

- Readiness probe на новой версии проверяет готовность к приёму трафика
- Graceful switchover: завершение активных транзакций на blue перед переключением

#### Redis — Recreate

**Стратегия:** Recreate (остановка → обновление → запуск)

**Обоснование:** Кэш без persistence (данные в памяти). Потеря данных допустима — кэш восстанавливается из PostgreSQL.

#### nginx — Graceful Reload

**Стратегия:** Graceful reload (обновление конфигурации без обрыва соединений)

**Обоснование:** API Gateway — критичная точка входа. Обновление конфигурации должно происходить без downtime.

**Процесс:**

1. Обновить конфигурационный файл (`nginx.conf`)
2. Проверить корректность: `nginx -t`
3. Применить изменения: `nginx -s reload`

**Zero-downtime контракт:**

- `nginx -s reload` запускает новые worker процессы с обновлённой конфигурацией
- Старые worker'ы завершают обработку активных запросов и останавливаются
- Новые запросы обрабатываются новыми worker'ами
- Активные соединения не обрываются

#### Подход к миграциям БД (Expand/Contract)

**Принцип:** Изменения схемы обратно совместимы с предыдущей версией приложения.

**Фаза 1: Expand** (добавление нового)

```sql
ALTER TABLE listings ADD COLUMN description_v2 TEXT;
UPDATE listings SET description_v2 = description WHERE description_v2 IS NULL;
```

**Код приложения (пишет в обе колонки, читает из новой)**

```go
db.Exec("UPDATE listings SET description = $1, description_v2 = $1 WHERE id = $2", desc, id)
db.QueryRow("SELECT description_v2 FROM listings WHERE id = $1", id).Scan(&desc)
```

**Фаза 2: Contract** (через 1 неделю, удаление старого)

```sql
ALTER TABLE listings DROP COLUMN description;
```

### 1.3. Observability

#### Алерты (4, Golden Signals)


| Сигнал         | Метрика                                              | Порог                | Окно  | Сервис                |
| -------------- | ---------------------------------------------------- | -------------------- | ----- | --------------------- |
| **Latency**    | `http_request_duration_p99{endpoint="/search"}`      | > 300 ms             | 5 min | Search Service        |
| **Errors**     | `http_requests_total{status=~"5.."}`                 | error rate > 1%      | 2 min | nginx (все эндпоинты) |
| **Traffic**    | `http_requests_total` (sum rate 1m)                  | < 100 RPS (аномалия) | 3 min | Search Service        |
| **Saturation** | `db_connection_pool_active / db_connection_pool_max` | > 0.85               | 5 min | Listing Service       |


#### Дашборды (3 уровня)

**Overview Dashboard**

- Golden Signals по всей системе: latency (p50/p95/p99), traffic (RPS), errors (%), saturation (CPU/RAM/pool)
- Infrastructure health: статус сервисов (health checks)

**Service-Level Dashboard**

- RED метрики по сервису: Rate (RPS по эндпоинтам), Errors (по статус-кодам), Duration (latency percentiles)

**Diagnostic Dashboard**

- Dependencies: PostgreSQL query latency, Redis hit rate, RabbitMQ lag
- Resource Usage: CPU, RAM, goroutines, throttling

#### Логи

**Формат:** JSON в stdout

**Обязательные поля:**


| Поле        | Назначение                                            |
| ----------- | ----------------------------------------------------- |
| `timestamp` | Время события (ISO8601, UTC)                          |
| `level`     | debug / info / warn / error / fatal                   |
| `service`   | Имя сервиса (listing-service, search-service, worker) |
| `trace_id`  | Distributed tracing ID (от X-Request-ID header)       |
| `msg`       | Описание события                                      |
| `error`     | Текст ошибки (если level=error)                       |


**Что логируем:**

- Входящий HTTP request (метод, path, query)
- Исходящий запрос к зависимостям (БД, Redis) если latency > 100ms
- Ошибки 5xx с stack trace
- Бизнес-события (модерация одобрена/отклонена, платёж успешен/провален)

**НЕ логируем:**

- PII (email, телефон, адрес)
- Секреты (JWT-токены, API keys, пароли)
- Полные тела ответов API

## 2. Доступность

### Целевая доступность системы


| Компонент                   | SLA    | Downtime/год | Обоснование                                                                          |
| --------------------------- | ------ | ------------ | ------------------------------------------------------------------------------------ |
| **Поиск и выдача карточек** | 99.95% | 4.4 часа     | Главная функция системы. Недоступность → пользователи уходят на конкурентов.         |
| **Оплата продвижения**      | 99.99% | 52 минуты    | Потеря платежей критична для выручки. Каждый час простоя → упущенная прямая выручка. |
| **Создание объявлений**     | 99.9%  | 8.7 часов    | Допустима кратковременная недоступность — пользователь повторит попытку позже.       |
| **Модерация**               | 99.9%  | 8.7 часов    | Задержка модерации допустима, не блокирует создание объявления.                      |


**Обоснование доступности поиска (99.95%):**
Поиск — главная точка входа пользователей. При простое на 1 час в пиковое время теряется доступ для ~10% активных пользователей, что приводит к оттоку на конкурентные площадки.

### RPO и RTO для критичных компонентов

#### PostgreSQL (БД)


| Показатель | Значение    | Реализация              |
| ---------- | ----------- | ----------------------- |
| **RPO**    | 0 секунд    | Синхронная репликация   |
| **RTO**    | < 30 секунд | Автоматический failover |


**Обоснование:** Платежи и объявления — критичные данные, потеря которых недопустима.

#### Redis (кэш)


| Показатель | Значение    | Реализация                        |
| ---------- | ----------- | --------------------------------- |
| **RPO**    | 100%        | Можем потерять данные, некритично |
| **RTO**    | < 10 секунд | Failover на replica               |


**Обоснование:** Кэш — производный компонент. Потеря допустима, данные восстанавливаются из PostgreSQL.

#### RabbitMQ


| Показатель | Значение   | Реализация                                       |
| ---------- | ---------- | ------------------------------------------------ |
| **RPO**    | 0 секунд   | Репликация очередей                              |
| **RTO**    | < 1 минута | Автоматический failover при падении одной из нод |


**Обоснование:** Задачи модерации нельзя потерять — объявление не будет опубликовано.

### Стратегия резервирования

#### PostgreSQL — Active/Standby

**Конфигурация:**

- Primary: pg1
- Standby: pg2 (синхронная реплика)
- Failover: автоматический

**Обоснование:** Транзакционная БД с ACID требует строгой консистентности. Active/active (multi-master) приведет к конфликтам записи.

**Геораспределённость:** Не требуется. Две зоны доступности внутри одного региона  достаточно для 99.95% SLA.

#### Redis — Master/Replica

**Конфигурация:**

- Master: r1
- Replica: r2
- Sentinel: 3 инстанса для кворума

**Обоснование:** Кэш не требует строгой консистентности, допустимо кратковременное рассогласование.

#### RabbitMQ — Quorum Queues (3-node cluster)

**Конфигурация:**

- Cluster: 3 ноды в разных зонах доступности
- Quorum queues: репликация на majority (2 из 3)

**Обоснование:** Критично не потерять задачи модерации — quorum queues гарантируют durability при падении 1 ноды.

#### Application Services — разные зоны доступности

**Конфигурация:**

- Replicas распределены: 50% в одной, 50% в другой
- Load balancer: envoy

### Maintenance Window

**Окно:** Вторник, 03:00–05:00 MSK

**Частота:** 1 раз в квартал

**Что выполняется:**

- Мажорные обновления PostgreSQL
- Миграция данных между хранилищами

**Коммуникация с пользователями:**

- За 7 дней: уведомление на главной странице + email
- Во время окна: статус-страница

### Текущая нагрузка (PoC)

| Компонент                | Конфигурация                | Цена (₽/мес) |
| ------------------------ | --------------------------- | ------------ |
| **Compute Cloud VM**     | 2 vCPU, 8 GB RAM, 72 GB HDD | 4400         |

#### Операционные затраты (₽/мес)


| Статья               | Расчёт                              | Стоимость |
| -------------------- | ----------------------------------- | --------- |

### Рост трафика: 2x (от ~50-60 RPS до ~100-120 RPS)

**Подход:** Вертикальное масштабирование VM

**Изменения:**


| Компонент            | Было                       | Стало                        | Δ цена    |
| -------------------- | -------------------------- | ---------------------------- | --------- |
| **Compute Cloud VM** | 2 vCPU, 8 GB RAM,72 GB HDD | 4 vCPU, 16 GB RAM,144 GB HDD | +4400     |
| Egress traffic       | 1000 GB                    | 2000 GB                      | +1420     |
| **Итого прирост**    |                            |                              | **+5820** |


**Инфраструктура:** 5870 + 5820 = **11690 ₽/мес**

**OpEx:** +40,000₽ (больше времени на поддержку при росте нагрузки) = **120,100 ₽/мес**

**TCO при 2x:** 11690 + 120100 = **131790 ₽/мес**

---

### Рост трафика: 5x (от ~50-60 RPS до ~250-300 RPS)

**Подход:** Переход на распределенную архитектуру (High Availability)

**Изменения:**


| Компонент         | Было                          | Стало                                              | Δ цена     |
| ----------------- | ----------------------------- | -------------------------------------------------- | ---------- |
| VM                | 1 × (2 vCPU, 8 GB, 72 GB HDD) | 2 × (4 vCPU, 16 GB, 144 GB HDD)                    | +13200     |
| Application LB    | Нет                           | Yandex ALB                                         | +1900      |
| PostgreSQL        | В контейнере                  | Managed PostgreSQL (2 nodes, 2 vCPU, 8 GB, 150 GB) | +9260      |
| Egress traffic    | 1000 GB                       | 5000 GB                                            | +5700      |
| **Итого прирост** |                               |                                                    | **+30060** |


**Инфраструктура:** 5870 + 30600 = **36470 ₽/мес**

**OpEx:** +60,000₽ (part-time DevOps для управления HA-конфигурацией) = **140,100 ₽/мес**

**TCO при 5x:** 36470 + 140100 = **176570 ₽/мес**

### Что дороже всего

**Для текущего PoC:**

- **VM (75% от инфраструктуры)** — единственный compute ресурс с docker-compose
- **OpEx (93% от TCO)** — разработка и поддержка превышают стоимость инфраструктуры

**При росте 5x:**

- **VM (48% от инфраструктуры)** — две VM для HA
- **Managed PostgreSQL (25%)** — переход на managed сервис для отказоустойчивости
- **Egress traffic (19%)** — значительный рост исходящего трафика
- **Application LB (5%)** — распределение нагрузки между VM
- **OpEx (79% от TCO)** — DevOps для управления распределенной системой

**Почему OpEx доминирует:**

- Инфраструктура дешевая (одна VM, docker-compose)
- Основные затраты — время разработчиков на поддержку и доработки
- При росте нужны дополнительные специалисты (DevOps, SRE)

**Как оптимизировать при дальнейшем росте:**

- Автоматизация (CI/CD, Infrastructure as Code) снижает Op
- Переход на Kubernetes позволяет горизонтально масштабировать compute без пропорционального роста OpEx
- Monitoring и алерты снижают время на incident response
